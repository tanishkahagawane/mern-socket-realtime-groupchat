15. What is the difference between `socket.emit()` and `socket.on()`?

## 15. What is the difference between `socket.emit()` and `socket.on()`?

Interview answer:

In Socket.IO, `socket.emit()` is used to send an event with data, while `socket.on()` is used to listen for an event and handle the received data.

- `socket.emit()` — sends an event.
- `socket.on()` — listens for an event and executes a callback when that event is received.

### Example

```
// Sender: emit an event
socket.emit("message", "Hello Server!");

// Receiver: listen for the event
socket.on("message", (data) => {
  console.log(data);
});
```

In this example, the sender emits a `message` event with the data `"Hello Server!"`. The receiver listens for the `message` event and processes the data when it arrives.

### Key differences

| Feature    | `socket.emit()`                              | `socket.on()`                                |
| ---------- | -------------------------------------------- | -------------------------------------------- |
| Purpose    | Sends an event                               | Listens for an event                         |
| Function   | Event emission                               | Event handling                               |
| Parameters | Event name and optional data                 | Event name and callback                      |
| Execution  | Sends the event to the intended recipient(s) | Runs the callback when the event is received |
| Example    | `socket.emit("chat", data)`                  | `socket.on("chat", callback)`                |

### Example in a client-server application

Client-side:

```
socket.emit("sendMessage", "Hello!");
```

Server-side:

```
io.on("connection", (socket) => {
  socket.on("sendMessage", (message) => {
    console.log(message);
    socket.emit("response", "Message received!");
  });
});
```

Here, the client emits `sendMessage`, the server listens for that event, and the server emits a `response` event back to that client.

Important interview point: `socket.emit()` does not automatically mean the server received or processed the event. If you need confirmation, Socket.IO supports acknowledgements using callback functions.

In short: `emit()` sends an event, whereas `on()` listens for an event and handles it when received.

16. What is the difference between `io.emit()`, `socket.emit()`, and `socket.broadcast.emit()`?

## 16. What is the difference between `io.emit()`, `socket.emit()`, and `socket.broadcast.emit()`?

Interview answer:

In Socket.IO, these three methods are used to send events to different sets of connected clients.

- `io.emit()` sends an event to all connected clients in the default namespace, including the sender.
- `socket.emit()` sends an event only to the specific client associated with that socket.
- `socket.broadcast.emit()` sends an event to all connected clients except the sender in the default namespace.

### Key differences

| Method                    | Who receives the event?               | Does the sender receive it? |
| ------------------------- | ------------------------------------- | --------------------------- |
| `io.emit()`               | All connected clients                 | Yes                         |
| `socket.emit()`           | Only the current socket's client      | Yes, as the recipient       |
| `socket.broadcast.emit()` | All clients except the current socket | No                          |

### Example code

```
io.on("connection", (socket) => {

  // 1. Send to all connected clients
  io.emit("message", "A user connected!");

  // 2. Send only to this client
  socket.emit("message", "Welcome!");

  // 3. Send to everyone except this client
  socket.broadcast.emit("message", "A new user joined!");
});
```

### Real-world example: Chat application

Suppose three users — A, B, and C — are connected to the server, and User A sends a message.

1\. `io.emit()`

User A Receives

User B Receives

User C Receives

2\. `socket.emit()`

User A Receives

User B No

User C No

3\. `socket.broadcast.emit()`

User A No

User B Receives

User C Receives

### When should we use each?

- `io.emit()` — broadcasting a global announcement or system-wide notification.
- `socket.emit()` — sending a private response, such as a welcome message or request result, to one client.
- `socket.broadcast.emit()` — notifying other users that someone joined a chat room or is typing.

Important interview point: These methods target clients connected to the relevant namespace. To broadcast only to a particular room, you can use `io.to("room1").emit(...)`. To send to a room while excluding the sender, use `socket.to("room1").emit(...)`.

In short: `io.emit()` sends to everyone, `socket.emit()` sends to one client, and `socket.broadcast.emit()` sends to everyone except the sender.


17. What is the difference between `socket.to(room).emit()` and `io.to(room).emit()`?

## 17. What is the difference between `socket.to(room).emit()` and `io.to(room).emit()`?

Interview answer:

In Socket.IO, both methods are used to send events to clients in a specific room. The main difference is whether the sender is excluded from receiving the message.

- `socket.to(room).emit()` sends an event to all clients in the specified room except the sender's socket.
- `io.to(room).emit()` sends an event to all clients in the specified room, including the sender if that socket belongs to the room.

### Key differences

| Feature                | `socket.to(room).emit()`           | `io.to(room).emit()`                    |
| ---------------------- | ---------------------------------- | --------------------------------------- |
| Target                 | Clients in the specified room      | Clients in the specified room           |
| Sender receives event? | No                                 | Yes, if the sender belongs to the room  |
| Common use case        | Broadcasting to other room members | Broadcasting to everyone in the room    |
| Scope                  | Room, excluding sender             | Room, including eligible sender sockets |

### Example

Suppose User A, User B, and User C are connected to a chat room named `room1`.

1\. Using `socket.to(room).emit()`

```
socket.to("room1").emit("message", "Hello everyone!");
```

- User A (sender): does not receive the event.
- User B: receives the event.
- User C: receives the event.

2\. Using `io.to(room).emit()`

```
io.to("room1").emit("message", "Hello everyone!");
```

- User A: receives the event if their socket is in `room1`.
- User B: receives the event.
- User C: receives the event.

### Real-world use cases

- `socket.to(room).emit()` — useful when a user sends a chat message and the server broadcasts it to other room members, while the sender already displays their own message.
- `io.to(room).emit()` — useful when the server needs to notify every room member, including the sender, about a shared event.

Important interview point: A socket does not automatically join an application-defined room. The server must first call `socket.join("room1")` for that socket to become a member.

In short: `socket.to(room).emit()` excludes the sender, whereas `io.to(room).emit()` includes all sockets in the room, including the sender if they are a member.

18. What are Socket.IO rooms, and how do they work?

## 18. What are Socket.IO rooms, and how do they work?

Interview answer:

Socket.IO rooms are logical groups of connected sockets that allow the server to send messages to a specific group of clients instead of broadcasting to everyone.

Rooms are managed on the server side. A socket can join one or more rooms, receive messages sent to those rooms, and leave rooms when necessary.

### How do rooms work?

1. Create or join a room: The server calls `socket.join(roomName)` to add a client to a room. A room is created implicitly when sockets join it.
2. Send messages to a room: The server uses `io.to(roomName).emit()` to broadcast an event to the room's members.
3. Exclude the sender: The server uses `socket.to(roomName).emit()` to send a message to other room members, excluding the current socket.
4. Leave a room: The server calls `socket.leave(roomName)` to remove a socket from the room.
5. Automatic cleanup: When a socket disconnects, it automatically leaves its rooms.

### Example

```
const io = require("socket.io")(3000);

io.on("connection", (socket) => {
  // Join a room
  socket.on("joinRoom", (roomName) => {
    socket.join(roomName);

    // Notify other room members
    socket.to(roomName).emit("userJoined", {
      message: "A new user joined the room"
    });
  });

  // Send a message to everyone in a room
  socket.on("chatMessage", ({ roomName, message }) => {
    io.to(roomName).emit("message", message);
  });

  // Leave a room
  socket.on("leaveRoom", (roomName) => {
    socket.leave(roomName);
  });
});
```

In this example, clients can join chat rooms, exchange messages with members of a particular room, and leave when they no longer want to participate.

### Real-world use cases

- Chat applications: Separate rooms for different conversations.
- Multiplayer games: Group players into individual game sessions.
- Live classes: Send announcements to students in a specific class.
- Notifications: Deliver updates to clients subscribed to a particular topic or group.

### Important interview points

- Rooms are server-side concepts; clients cannot directly manage room membership through the Socket.IO client API.
- A socket can belong to multiple rooms simultaneously.
- Room membership is automatically cleaned up when a socket disconnects.
- In a multi-server deployment, room broadcasting across servers requires a suitable shared adapter, such as the Redis adapter.

In short: Socket.IO rooms group connected clients so the server can efficiently target messages to specific users or groups without broadcasting to every connected client.

19. What is the difference between rooms and namespaces?

## 19. What is the difference between rooms and namespaces in Socket.IO?

Interview answer:

In Socket.IO, namespaces separate communication channels within a single connection, while rooms group sockets within a namespace so the server can send messages to specific groups of clients.

Namespaces help organize different parts of an application, whereas rooms help target messages to particular users or groups.

### Key differences

| Feature         | Rooms                                 | Namespaces                                            |
| --------------- | ------------------------------------- | ----------------------------------------------------- |
| Purpose         | Group sockets for targeted messaging  | Separate communication channels                       |
| Scope           | Exist within a namespace              | Logical communication endpoint                        |
| Connection      | Uses an existing namespace connection | Each namespace has its own Socket.IO connection state |
| Identification  | Room name, such as `room1`            | Namespace path, such as `/chat`                       |
| Joining         | `socket.join("room1")`                | Client connects to the namespace                      |
| Messaging       | `io.to("room1").emit()`               | `io.of("/chat").emit()`                               |
| Common use case | Chat groups, game sessions            | Chat, notifications, administration channels          |

### 1. Rooms example

Rooms allow selected clients within the same namespace to receive messages.

```
io.on("connection", (socket) => {
  socket.join("developers");

  io.to("developers").emit(
    "message",
    "Hello, developers!"
  );
});
```

Here, only sockets in the `developers` room receive the event.

### 2. Namespaces example

Namespaces separate different communication channels within the same Socket.IO server.

```
const chat = io.of("/chat");
const notifications = io.of("/notifications");

chat.on("connection", (socket) => {
  console.log("Chat user connected");
});

notifications.on("connection", (socket) => {
  console.log("Notification user connected");
});
```

Clients connect to the desired namespace:

```
const chatSocket = io("https://example.com/chat");

const notificationSocket =
  io("https://example.com/notifications");
```

Each namespace can have its own event handlers, middleware, and room membership. Namespaces typically share the underlying connection when they use the same Socket.IO Manager and origin, rather than necessarily opening separate network connections.

### Real-world example

Imagine a learning platform:

- Namespaces: `/students`, `/teachers`, and `/admin` separate different application channels.
- Rooms: `class-101`, `class-102`, and `math-group` target specific groups within a namespace.

Socket.IO server

/students

class-101

class-102

/teachers

math-group

science-group

/admin

admin-alerts

Namespaces separate channels; rooms group sockets within each channel.

### Interview conclusion

"Namespaces are used to separate different communication channels within a Socket.IO application, while rooms are used to group sockets within a namespace for targeted broadcasting. For example, I might use a `/chat` namespace and create separate rooms for individual chat groups."

20. How do you send a message to a specific connected client?
## 20. How do you send a message to a specific connected client in Socket.IO?

In Socket.IO, you can send a message to a specific connected client using that client's socket ID and the `io.to(socketId).emit()` method.

### 1. Example: Send a message to a specific client

Server-side code (Node.js):

```
io.on("connection", (socket) => {
  console.log("Client connected:", socket.id);

  // Send a message only to this client
  socket.emit("welcome", "Welcome to the server!");
});
```

Here, `socket.emit()` sends the message only to the client associated with that socket.

### 2. Send a message using the socket ID

If you want to send a message to a particular client from somewhere else in your server code, use `io.to(socketId).emit()`.

```
io.on("connection", (socket) => {
  const clientId = socket.id;

  // Send a message to this specific client
  io.to(clientId).emit("privateMessage", {
    message: "Hello, specific client!"
  });
});
```

- `io.to(socketId)` targets the client identified by that socket ID.
- `.emit()` sends the event and its data.
- Other connected clients do not receive the message.

### 3. Example: Send a message to a particular user

In a real application, you usually identify users by their application-level user ID rather than relying on a socket ID, because a user may reconnect and receive a new socket ID.

```
const userSockets = new Map();

io.on("connection", (socket) => {
  const userId = socket.handshake.auth.userId;

  userSockets.set(userId, socket.id);

  socket.on("disconnect", () => {
    if (userSockets.get(userId) === socket.id) {
      userSockets.delete(userId);
    }
  });
});

// Send a message to a particular user
function sendMessageToUser(userId, message) {
  const socketId = userSockets.get(userId);

  if (socketId) {
    io.to(socketId).emit("privateMessage", message);
  }
}
```

Important: In production, authenticate the user before trusting their identity, and handle multiple connections per user if needed. An alternative is to put all of a user's sockets in a room named for that user and send with `io.to(userRoom).emit(...)`.

### Interview-ready answer

“In Socket.IO, we can send a message to a specific connected client using `socket.emit()` when handling that client's connection, or `io.to(socketId).emit()` when targeting a client from elsewhere in the server. For real applications, we generally map authenticated user IDs to socket IDs or use user-specific rooms, because socket IDs can change after reconnection.”

21. How do you handle connection and disconnection events?

## 21. How do you handle connection and disconnection events in Socket.IO?

In Socket.IO, we handle connection and disconnection events using the `connection` and `disconnect` events on the server.

- `connection` fires when a client successfully connects to the server.
- `disconnect` fires when a client disconnects, for example, due to closing the browser tab or losing network connectivity.

### 1. Example: Handle connection and disconnection

Server-side code (Node.js):

```
const { Server } = require("socket.io");

const io = new Server(3000);

io.on("connection", (socket) => {
  console.log("Client connected:", socket.id);

  // Listen for client events
  socket.on("chatMessage", (message) => {
    console.log("Received message:", message);
  });

  // Handle disconnection
  socket.on("disconnect", (reason) => {
    console.log("Client disconnected:", socket.id);
    console.log("Reason:", reason);
  });
});
```

### 2. Common disconnection reasons

| Reason                        | Meaning                                                   |
| ----------------------------- | --------------------------------------------------------- |
| `client namespace disconnect` | The client intentionally disconnected from the namespace. |
| `server namespace disconnect` | The server disconnected the client from the namespace.    |
| `ping timeout`                | The client did not respond to the heartbeat in time.      |
| `transport close`             | The underlying connection closed.                         |
| `transport error`             | A transport-level error occurred.                         |

### 3. What should you do during these events?

On connection:

- Authenticate the user and initialize their session.
- Join relevant rooms.
- Register event listeners.
- Update online status if needed.

On disconnection:

- Remove temporary resources and clean up listeners or subscriptions.
- Update the user's online status if appropriate.
- Handle room membership—Socket.IO automatically removes the disconnected socket from its rooms.
- Preserve important application data in persistent storage rather than relying on the socket connection.

### 4. Client-side connection handling

You can also listen for these events on the client:

```
const socket = io("http://localhost:3000");

socket.on("connect", () => {
  console.log("Connected:", socket.id);
});

socket.on("disconnect", (reason) => {
  console.log("Disconnected:", reason);
});
```

Note that `connect` may fire again after automatic reconnection, so connection-related setup should be designed to run safely more than once.

### Interview-ready answer

“In Socket.IO, I use the server-side `connection` event to detect when a client connects and the socket's `disconnect` event to detect when it leaves. On connection, I handle authentication, room joining, and initialization. On disconnection, I clean up resources and update online status if necessary. I also inspect the disconnect reason to understand whether the issue was caused by a timeout, transport failure, or intentional disconnect.”

22. How do you implement acknowledgements in Socket.IO?

## 22. How do you implement acknowledgements in Socket.IO?

In Socket.IO, acknowledgements allow the sender to know whether the receiver processed an event and optionally receive a response.

They work by passing a callback function along with the event data. The receiver calls that callback when it has processed the event.

### 1. Basic acknowledgement example

Server-side code:

```
io.on("connection", (socket) => {
  socket.on("sendMessage", (message, callback) => {
    console.log("Received:", message);

    // Acknowledge the event
    callback({
      success: true,
      message: "Message received successfully"
    });
  });
});
```

Client-side code:

```
socket.emit("sendMessage", "Hello server!", (response) => {
  console.log(response);
});
```

Output:

```
{
  success: true,
  message: "Message received successfully"
}
```

Here, the client sends an event, and the server invokes the callback to return an acknowledgement.

### 2. Acknowledgements with timeout

You can set a timeout so the sender doesn't wait indefinitely for an acknowledgement.

```
socket.timeout(5000).emit("sendMessage", "Hello!", (err, response) => {
  if (err) {
    console.log("Acknowledgement timed out");
  } else {
    console.log("Server response:", response);
  }
});
```

- `5000` means the client waits up to five seconds.
- If no acknowledgement arrives in time, `err` is set.
- Otherwise, `response` contains the acknowledgement data.

### 3. When are acknowledgements useful?

- Confirming that a chat message was received or processed.
- Confirming that a database operation completed.
- Returning validation errors or success status.
- Detecting when a server doesn't respond within a specified time.

Important: An acknowledgement confirms only what the receiver's code reports. It does not automatically guarantee that data was permanently saved or that a message was delivered to its final recipient. For critical operations, combine acknowledgements with validation, persistent storage, and suitable retry or deduplication logic.

### Interview-ready answer

“In Socket.IO, acknowledgements are implemented by passing a callback function with `socket.emit()`. The receiver invokes that callback to return a response to the sender. We can also use `socket.timeout()` to detect when an acknowledgement doesn't arrive within a specified time. Acknowledgements are useful for confirming event processing, handling errors, and implementing request-response communication over Socket.IO.”
