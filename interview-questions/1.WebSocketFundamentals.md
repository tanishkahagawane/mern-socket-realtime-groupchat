## 1. WebSocket Fundamentals

1. What are WebSockets, and why are they used?

WebSockets are a communication protocol that enables two-way, real-time communication between a client and a server over a single, persistent connection.

Unlike HTTP, where the client typically sends a request and the server returns a response, WebSockets allow both the client and server to send messages independently without repeatedly establishing new connections.

Why are WebSockets used?

- Real-time communication: To exchange data instantly between the client and server.
- Low latency: Reduces the overhead of repeatedly sending HTTP requests.
- Bidirectional communication: Both client and server can send data at any time.
- Efficient data transfer: Maintains a persistent connection for continuous communication.

Examples of use cases:

- Chat applications and messaging systems.
- Live stock market updates.
- Online multiplayer games.
- Real-time notifications and dashboards.

Example: In a chat application, when one user sends a message, the server can immediately push that message to the other user through a WebSocket connection without requiring the receiver to refresh the page or continuously poll the server.

In short: WebSockets are used when an application requires fast, efficient, and continuous two-way communication between the client and server.

---

2. How do WebSockets work internally?

WebSockets work by establishing a persistent, full-duplex connection between a client and a server over a single TCP connection. Once the connection is established, both sides can send and receive data independently without repeatedly creating new connections.

The internal working involves the following steps:

1\. Connection Initiation: The client sends an HTTP request to the server with an `Upgrade: websocket` header to request a WebSocket connection.

2\. Handshake: The server validates the request and responds with `HTTP 101 Switching Protocols` if it accepts the upgrade.

3\. Connection Establishment: The HTTP connection is upgraded to a WebSocket connection, which remains open until either side closes it or the connection is interrupted.

4\. Data Exchange: Both the client and server can send messages at any time using WebSocket frames. This supports real-time, bidirectional communication.

5\. Connection Management: WebSockets support ping and pong control frames to check whether the connection is still alive. Applications may also implement reconnection logic if the connection drops.

6\. Connection Closure: Either side can initiate a closing handshake, allowing the connection to close gracefully.

Example: In a chat application, when a user sends a message, the client sends it through the established WebSocket connection. The server processes the message and forwards it to the recipient over their WebSocket connection, allowing the message to appear instantly without repeated HTTP requests.

In short: WebSockets start with an HTTP handshake, upgrade to a persistent TCP connection, exchange data through frames in both directions, and close through a closing handshake.

3. What is the difference between WebSockets and HTTP?

HTTP and WebSockets are communication protocols used between clients and servers, but they differ in how they handle communication.

HTTP follows a request-response model, where the client sends a request and the server returns a response. WebSockets provide persistent, bidirectional communication, allowing both the client and server to send data at any time.

### Key differences

| Feature           | HTTP                                                         | WebSockets                                   |
| ----------------- | ------------------------------------------------------------ | -------------------------------------------- |
| Communication     | Request-response                                             | Full-duplex, bidirectional                   |
| Connection        | Typically handled per request, with connections often reused | Persistent connection                        |
| Data transfer     | Usually initiated by the client                              | Initiated by either client or server         |
| Overhead          | Repeated request headers can add overhead                    | Lower overhead after the initial handshake   |
| Real-time updates | Often uses polling or other techniques                       | Supports real-time message delivery          |
| Protocol          | HTTP or HTTPS                                                | WS or WSS                                    |
| Best use cases    | REST APIs, web pages, CRUD operations                        | Chat apps, live notifications, online gaming |

### Example

- HTTP: A user clicks a button to fetch product details. The client sends a request, and the server returns the product data.
- WebSockets: In a chat application, when one user sends a message, the server can immediately push it to the recipient without the recipient repeatedly requesting new messages.

### When should we use each?

- Use HTTP for standard API calls, form submissions, fetching data, and CRUD operations.
- Use WebSockets when you need continuous, low-latency, two-way communication, such as live chats, multiplayer games, or real-time dashboards.

In short: HTTP is primarily request-response based, whereas WebSockets enable persistent, bidirectional communication over a single connection. WebSockets are not always better; the right choice depends on the application's requirements.

4. What is the difference between WebSockets, short polling, and long polling?
4\. What is the difference between WebSockets, Short Polling, and Long Polling?

WebSockets, short polling, and long polling are techniques used to exchange data between a client and a server. The main difference is how the client receives updates from the server.

### 1. Short Polling

In short polling, the client sends requests to the server at regular intervals to check whether new data is available.

- The server responds immediately, even if there is no new data.
- It is simple to implement but can generate many unnecessary requests.
- It may introduce delays between updates.

Example: A chat application checks for new messages every 5 seconds.

### 2. Long Polling

In long polling, the client sends a request, and the server holds the request open until new data becomes available or a timeout occurs. The client then receives the response and sends another request.

- Reduces unnecessary requests compared with short polling.
- Provides near-real-time updates.
- Requires repeated HTTP requests and can consume server resources while requests are waiting.

Example: A notification system keeps a request open until a new notification arrives, then sends another request.

### 3. WebSockets

WebSockets establish a persistent, bidirectional connection between the client and server.

- Both sides can send data at any time.
- No need to repeatedly send HTTP requests to check for updates.
- Well suited for frequent, low-latency communication.

Example: A live chat application instantly delivers messages between users through an established WebSocket connection.

## Key differences

| Feature         | Short Polling               | Long Polling                           | WebSockets                       |
| --------------- | --------------------------- | -------------------------------------- | -------------------------------- |
| Communication   | Repeated request-response   | Request waits for an update or timeout | Bidirectional                    |
| Connection      | Separate polling requests   | Repeated, long-held requests           | Persistent connection            |
| Server response | Immediate                   | When data arrives or timeout occurs    | Whenever data is sent            |
| Latency         | Depends on polling interval | Usually low                            | Usually very low                 |
| Overhead        | High                        | Moderate                               | Low after handshake              |
| Implementation  | Simple                      | Moderate                               | Requires WebSocket support       |
| Best use case   | Infrequent updates          | Near-real-time updates over HTTP       | Frequent real-time communication |

## How they work visually

Client  -> <- Server
Request → Response → Wait → Repeat

Long polling
Client  -> Server waits
Request → Wait for data → Response → Repeat

WebSockets
Client -> <- Server
Persistent connection → Messages in either direction at any time

## Interview conclusion

“Short polling repeatedly checks the server at fixed intervals, while long polling holds an HTTP request until data becomes available or a timeout occurs. WebSockets establish a persistent, bidirectional connection that allows the client and server to exchange messages at any time. Therefore, WebSockets are generally preferred for frequent real-time communication, while polling techniques can be suitable for simpler applications or less frequent updates.”

5. What is a full-duplex connection?

A full-duplex connection is a communication system in which both the client and server can send and receive data simultaneously over the same connection.

In WebSockets, full-duplex communication allows the client and server to exchange messages independently without waiting for the other side to finish sending data.

Example: In a chat application, User A can send a message to User B while User B is simultaneously sending a message to User A. Both messages can travel over their respective WebSocket connections without blocking each other.

### Types of communication

| Type        | Description                                           | Example                                 |
| ----------- | ----------------------------------------------------- | --------------------------------------- |
| Simplex     | Data flows in only one direction                      | Traditional TV broadcast                |
| Half-duplex | Data flows in both directions, but not simultaneously | Walkie-talkie                           |
| Full-duplex | Data flows in both directions simultaneously          | Telephone call, WebSocket communication |

In short: Full-duplex means both sides can send and receive data simultaneously. This makes WebSockets suitable for real-time applications such as chat systems, online gaming, and live collaboration tools.

6. What happens during a WebSocket handshake?

6\. What happens during a WebSocket handshake?

A WebSocket handshake is the initial process in which the client and server establish a WebSocket connection. It starts as an HTTP request and upgrades to the WebSocket protocol if the server accepts the request.

### Steps involved in a WebSocket handshake

1\. Client sends an HTTP request

The client sends an HTTP GET request to the server with headers requesting an upgrade to the WebSocket protocol.

Example:

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

- `Upgrade: websocket` requests switching to WebSockets.
- `Connection: Upgrade` indicates that the connection should be upgraded.
- `Sec-WebSocket-Key` contains a random Base64-encoded nonce used in the handshake.
- `Sec-WebSocket-Version: 13` specifies the WebSocket protocol version.

2\. Server validates the request

The server checks whether the request is valid and whether it supports the WebSocket protocol.

3\. Server sends a handshake response

If the server accepts the request, it responds with HTTP status `101 Switching Protocols`.

Example:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

The `Sec-WebSocket-Accept` value is calculated from the client's `Sec-WebSocket-Key` using a defined hashing procedure. This helps confirm that the server understands the WebSocket handshake.

4\. Connection is established

After the successful handshake, communication switches from HTTP to the WebSocket protocol. Both client and server can now exchange WebSocket frames over the established connection.

### Important points for an interview

- The WebSocket handshake begins with an HTTP request.
- A successful handshake returns HTTP `101 Switching Protocols`.
- The handshake establishes the connection; it does not carry the application messages themselves.
- After the upgrade, data is exchanged using WebSocket frames rather than ordinary HTTP request-response messages.
- For secure WebSockets, `wss://` uses TLS in addition to the WebSocket handshake.

In short: A WebSocket handshake is the process of upgrading an HTTP connection to a WebSocket connection using a request from the client and a `101 Switching Protocols` response from the server.

7. What is the difference between `ws://` and `wss://`?

7\. What is the difference between `ws://` and `wss://`?

`ws://` and `wss://` are WebSocket URL schemes used to establish communication between a client and a server.

The main difference is that `wss://` provides encrypted communication using TLS, whereas `ws://` does not provide transport-layer encryption.

| Feature         | `ws://`                                      | `wss://`                 |
| --------------- | -------------------------------------------- | ------------------------ |
| Full form       | WebSocket                                    | WebSocket Secure         |
| Security        | No TLS encryption                            | Uses TLS encryption      |
| Data protection | Data can be intercepted or read in transit   | Protects data in transit |
| Default port    | 80                                           | 443                      |
| Use case        | Local development or controlled environments | Production applications  |
| URL example     | `ws://example.com/chat`                      | `wss://example.com/chat` |

### Example

```
// Unencrypted WebSocket
const socket1 = new WebSocket("ws://example.com/chat");

// Secure WebSocket
const socket2 = new WebSocket("wss://example.com/chat");
```

In the first example, the communication is not encrypted at the transport layer. In the second example, TLS encrypts the communication between the client and the server.

### Why is `wss://` preferred?

- Confidentiality: Helps prevent unauthorized parties from reading transmitted data.
- Integrity: Helps detect unauthorized modification of data in transit.
- Authentication: TLS certificates help the client verify the server's identity.
- Browser security: Secure WebSocket connections are generally required when a website served over HTTPS connects to a WebSocket server.

### Interview conclusion

"`ws://` is the non-TLS WebSocket protocol, while `wss://` is the secure version that uses TLS to encrypt communication. In production applications, we generally prefer `wss://` to protect sensitive data and meet browser security requirements."

8. What are ping, pong, and close frames?

8\. What are Ping, Pong, and Close frames in WebSockets?

Ping, Pong, and Close are control frames in the WebSocket protocol used to check connection health and manage connection termination.

### 1. Ping Frame

A Ping frame is sent by the client or server to check whether the other side is still responsive.

- It helps detect unresponsive connections.
- The receiver is expected to respond with a Pong frame.
- It can optionally contain a small payload.

### 2. Pong Frame

A Pong frame is the response to a Ping frame.

- It indicates that the receiver is responding.
- It typically carries the same payload as the Ping frame.
- It can also be sent independently as a heartbeat by an implementation.

### 3. Close Frame

A Close frame is used to initiate a graceful WebSocket connection shutdown.

- Either the client or server can send it.
- It may contain a status code and a reason for closing.
- The other side normally responds with a Close frame, after which the underlying connection is closed.

### Example use case

In a real-time chat application, the server may periodically send Ping frames to verify that a client is still responsive. If the expected Pong does not arrive within a timeout, the server may consider the connection dead and clean it up. When a user logs out, the client can send a Close frame to shut down the connection gracefully.

### Interview conclusion

"Ping and Pong frames are used for connection health checks and heartbeats, while Close frames are used to terminate a WebSocket connection gracefully. These control frames help maintain reliable connections and manage their lifecycle."

## 2. WebSocket vs Socket.IO

9. What is Socket.IO, and why is it used?

9\. What is Socket.IO, and why is it used?

Socket.IO is a JavaScript library that enables real-time, bidirectional, event-based communication between clients and servers. It is commonly used to build applications that need instant data exchange, such as chat applications, live notifications, and real-time dashboards.

Socket.IO often uses WebSocket as its transport, but it can fall back to HTTP long polling when WebSocket connections are unavailable.

### Why is Socket.IO used?

1. Real-time communication: Sends messages between client and server instantly.
2. Automatic reconnection: Attempts to reconnect when a connection is interrupted.
3. Fallback support: Can use HTTP long polling if WebSocket transport is unavailable.
4. Event-based communication: Allows sending and receiving named events, such as `message`, `notification`, or `userJoined`.
5. Rooms and namespaces: Makes it easier to organize clients and broadcast messages to specific groups.
6. Broadcasting: Supports sending messages to multiple connected clients.

### Example

Using Socket.IO with Node.js:

Server-side code:

```
const { Server } = require("socket.io");

const io = new Server(3000);

io.on("connection", (socket) => {
  console.log("Client connected");

  socket.on("message", (data) => {
    io.emit("message", data);
  });

  socket.on("disconnect", () => {
    console.log("Client disconnected");
  });
});
```

Client-side code:

```
const socket = io("http://localhost:3000");

socket.emit("message", "Hello Server!");

socket.on("message", (data) => {
  console.log(data);
});
```

In this example, when a client sends a `message` event, the server broadcasts that message to all connected clients.

### Difference between WebSockets and Socket.IO

| Feature                | WebSockets                     | Socket.IO                       |
| ---------------------- | ------------------------------ | ------------------------------- |
| Type                   | Communication protocol         | Communication library           |
| Communication          | Bidirectional                  | Bidirectional, event-based      |
| Automatic reconnection | Must be implemented separately | Supported by default            |
| Fallback transport     | No built-in fallback           | Supports HTTP long polling      |
| Rooms and broadcasting | Must be implemented separately | Built-in support                |
| Compatibility          | Standard protocol              | Requires Socket.IO on both ends |

Important: Socket.IO is not the same as a native WebSocket connection. A Socket.IO client cannot directly communicate with a plain WebSocket server because Socket.IO uses its own protocol on top of its underlying transport.

### Interview conclusion

"Socket.IO is a real-time communication library built around events. It simplifies real-time application development by providing features such as automatic reconnection, broadcasting, rooms, and fallback transports. Unlike native WebSockets, it provides additional functionality that developers would otherwise need to implement themselves."

12. How does Socket.IO establish and maintain a connection?

## 12. How does Socket.IO establish and maintain a connection?

Interview answer:

Socket.IO establishes a connection between the client and server using its own protocol. By default, it typically starts with HTTP long polling and attempts to upgrade to WebSocket when possible. It then maintains the connection using heartbeat mechanisms, handles disconnections, and automatically attempts reconnection when the connection is lost.

### Steps involved

1\. Connection initiation

The client connects to the Socket.IO server using the `io()` method.

```
const socket = io("http://localhost:3000");
```

2\. Transport establishment

By default, Socket.IO generally starts with HTTP long polling. If WebSocket is available, it attempts to upgrade the transport to WebSocket.

3\. Handshake and connection

The Socket.IO client and server exchange protocol messages to establish a session. The server assigns a Socket.IO session ID, and the connection event is triggered once the Socket.IO connection is established.

4\. Event-based communication

Once connected, the client and server exchange data through named events using `emit()` and `on()`.

```
socket.emit("message", "Hello Server");

socket.on("message", (data) => {
  console.log(data);
});
```

5\. Connection maintenance

Socket.IO uses heartbeat messages, including Engine.IO ping and pong packets, to check whether the connection is alive. If the connection becomes unresponsive, it can be considered disconnected.

6\. Automatic reconnection

If the connection drops, the client automatically attempts to reconnect using a retry strategy with delays. The application can also listen for connection and disconnection events.

```
socket.on("connect", () => {
  console.log("Connected:", socket.id);
});

socket.on("disconnect", (reason) => {
  console.log("Disconnected:", reason);
});

socket.on("connect_error", (error) => {
  console.log("Connection error:", error.message);
});
```

### Connection flow

1\. Client calls `io()`

2\. Establish transport

HTTP long polling by default

3\. Upgrade to WebSocket

If supported and possible

4\. Exchange events

`emit()` and `on()`

5\. Maintain connection

Heartbeat and reconnection handling

### Important interview points

- Socket.IO uses the Engine.IO layer to manage transports and connection health.
- WebSocket is generally preferred when available, but Socket.IO can use HTTP long polling.
- Heartbeats detect unresponsive connections.
- Automatic reconnection does not guarantee that missed application messages will be recovered; message recovery or persistence may need to be implemented separately.
- A successful reconnection may create a new session, so applications should not assume the previous socket ID remains unchanged.

In short: Socket.IO establishes a session using Engine.IO, negotiates an appropriate transport, exchanges events, monitors connection health with heartbeats, and automatically attempts to reconnect after interruptions.


13. What is transport fallback in Socket.IO?

## 13. What is transport fallback in Socket.IO?

Interview answer:

Transport fallback in Socket.IO is the ability to use an alternative communication transport when the preferred transport, such as WebSocket, is unavailable or cannot be established.

Socket.IO typically starts with HTTP long polling and then attempts to upgrade to a WebSocket connection. If WebSocket cannot be established, it can continue using HTTP long polling, provided that transport remains available.

### How does it work?

1. Connection initiation: The client initiates a connection to the Socket.IO server.
2. Initial transport: By default, Socket.IO typically establishes the connection using HTTP long polling.
3. Transport upgrade: The client attempts to upgrade the connection to WebSocket.
4. Fallback: If WebSocket is unavailable or the upgrade fails, Socket.IO can continue using HTTP long polling.
5. Communication continues: The client and server can continue exchanging events using the available transport.

### Example

Suppose a user accesses a chat application from a network that blocks WebSocket connections.

- With native WebSockets alone, the connection attempt may fail unless the application implements another transport.
- With Socket.IO, the client can use HTTP long polling to continue communicating with the server.

### Transport fallback flow

Client initiates Socket.IO connection

Start with HTTP long polling

Attempt WebSocket upgrade

Success

Use WebSocket

Failure

Continue polling

### Why is transport fallback useful?

- Improves connectivity across restrictive networks and proxies.
- Helps applications communicate when WebSocket connections are blocked.
- Reduces the need to implement fallback logic manually.
- Improves compatibility across different environments.

Important interview point: Socket.IO's default connection strategy typically begins with HTTP long polling and upgrades to WebSocket. It does not necessarily try WebSocket first and then fall back. The exact behavior can also be changed through client transport configuration.

In short: Transport fallback allows Socket.IO to maintain real-time communication through an alternative transport, such as HTTP long polling, when WebSocket is unavailable.


14. How does automatic reconnection work in Socket.IO?

## 14. How does automatic reconnection work in Socket.IO?

Interview answer:

Socket.IO provides a built-in automatic reconnection mechanism that allows the client to attempt to reconnect to the server when the connection is unexpectedly lost.

When a disconnection occurs, the Socket.IO client waits for a configured delay and then attempts to reconnect. If the attempt fails, it retries according to its reconnection settings, typically using an increasing delay with randomization to avoid overwhelming the server with simultaneous reconnection attempts.

### How does it work?

1. Connection loss: The client detects that the connection to the server has been interrupted.
2. Retry delay: The client waits before attempting to reconnect.
3. Reconnection attempt: The client tries to establish a new Socket.IO connection.
4. Retry on failure: If reconnection fails, the client waits longer before the next attempt, up to the configured maximum delay.
5. Connection restored: When reconnection succeeds, the `connect` event is triggered again, allowing the application to resume communication.

### Example

```
const socket = io("https://example.com", {
  reconnection: true,
  reconnectionAttempts: 5,
  reconnectionDelay: 1000,
  reconnectionDelayMax: 5000,
  randomizationFactor: 0.5
});

socket.on("connect", () => {
  console.log("Connected:", socket.id);
});

socket.on("disconnect", (reason) => {
  console.log("Disconnected:", reason);
});

socket.on("connect_error", (error) => {
  console.log("Connection failed:", error.message);
});
```

Explanation of the configuration:

- `reconnection: true` — enables automatic reconnection.
- `reconnectionAttempts: 5` — limits the number of reconnection attempts.
- `reconnectionDelay: 1000` — sets the initial delay to 1 second.
- `reconnectionDelayMax: 5000` — caps the delay at 5 seconds.
- `randomizationFactor: 0.5` — adds randomization to retry delays.

These are configurable settings; the values above are examples rather than required defaults.

### Important interview points

- Socket.IO handles reconnection automatically on the client by default.
- Retry delays generally increase up to a configured maximum, with randomization.
- A successful reconnection may result in a new socket ID.
- Automatic reconnection does not guarantee that messages missed during disconnection will be delivered. Applications may need acknowledgements, retries, message persistence, or connection-state recovery.
- If the server deliberately disconnects a client using a server-side disconnect operation, the client does not automatically reconnect in the same way; the application must explicitly reconnect if appropriate.

In short: Socket.IO automatically detects unexpected disconnections and retries connecting with configurable delays and retry limits, helping real-time applications recover from temporary network failures.
